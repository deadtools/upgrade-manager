# Universal Upgrade Manager 3.7.4

## Подключение к базе данных — 3.7.4

В «Настройки → Подключение к базе данных» доступны три источника: автоопределение CMS, конкретный локальный файл конфигурации и ручные реквизиты MySQL/MariaDB. Для режима «Файл конфигурации» можно указать относительный или абсолютный путь к PHP/.env-файлу; Upgrade Manager читает из него host, port, имя БД, пользователя, пароль и префикс. В ручном режиме пароль хранится только в зашифрованном runtime-файле и не включается в релизные ZIP или публичные профили.


## SMTP для писем безопасности 3.6.2

На центральном сайте откройте **Настройки → SMTP для писем безопасности**. Укажите SMTP-сервер, порт, режим шифрования, логин/пароль и адрес отправителя. Кнопка **Проверить подключение** проверяет TLS и SMTP AUTH, а **Отправить тестовое письмо** подтверждает фактическую передачу письма SMTP-серверу. Recovery и восстановление пароля используют SMTP, когда он включён. Пока SMTP выключен, сохраняется legacy fallback через PHP `mail()`.


## Авторизация, восстановление пароля и Recovery 3.6.1

Новые установки больше не используют логин `admin` и постоянный Recovery key. На `/upgrade/setup.php` администратор задаёт **email + пароль**; email становится логином Upgrade Manager.

Recovery работает по одноразовой ссылке: на `/upgrade/recovery.php` вводится email администратора, клиент подтверждает его локально и просит центральный сервер Upgrade Manager отправить письмо. Ссылка подписана RSA-ключом центрального сервера, привязана к `site_id`, домену и email, действует 10 минут и используется только один раз. После открытия создаётся Recovery-сессия на 15 минут.

После обновления старой установки прежний логин (обычно `admin`) продолжает работать для первого входа. Затем раздел «Безопасность» обязательно попросит привязать email администратора; после привязки именно email используется для обычного входа и Recovery.

Начиная с 3.5.4 восемь неверных попыток входа с одного сетевого источника включают 15-минутную блокировку ещё до проверки пароля. Смена пароля или email увеличивает `session_generation` и отзывает прежние cookie-сессии.

Самостоятельный защищённый модуль `/upgrade/` предназначен для файловых патчей, резервных копий, rollback и работы через OAuth 2.1 + MCP. При установке определяется CMS и создаётся профиль возможностей/защиты найденного сайта.


## Перенос проекта между доменами — 3.5.0

В «Настройках» добавлен отдельный блок **«Перенос проекта»**. Старый сайт создаёт временную HTTPS-ссылку миграции на 24 часа. Ссылка содержит полный файловый архив сайта (кроме `/upgrade/` и служебного storage Upgrade Manager) и полный дамп обнаруженной MySQL/MariaDB.

На новом домене сначала устанавливается Upgrade Manager. Затем через **«Импортировать проект сюда»** вставляется ссылка со старого сайта и локально вводятся реквизиты новой БД: host/port, имя БД, пользователь и пароль. Эти реквизиты старому серверу не передаются.

До первого изменения нового сайта Upgrade Manager скачивает и проверяет исходные данные, распаковывает проект во временный staging, автоматически переписывает конфиг БД для поддерживаемых CMS/типовых PHP-конфигураций и делает страховочную копию уже существующих файлов и новой БД. Начиная с 3.5.2 полный дамп MySQL/MariaDB сохраняет не только базовые таблицы и данные, но также VIEW, triggers, procedures, functions и events; generated columns не вставляются вручную, а данные InnoDB выгружаются под consistent snapshot. При нетранзакционных таблицах используется read-lock, и если сервер не разрешает безопасный lock, миграция останавливается до любых изменений.

На новом сервере до начала очистки дополнительно проверяется `max_allowed_packet` относительно самого большого SQL-выражения дампа. Затем импортируется БД, безопасно меняется старый домен и абсолютный путь в строковых/serialized значениях, устанавливаются файлы и выполняется финальная проверка набора объектов БД. При ошибке или прерывании после начала изменений запускается автоматический rollback нового сайта, использующий такой же полный дамп v2. После успешного переноса источник получает команду удалить временный migration package.

Начиная с 3.5.4 URL источника дополнительно защищён от SSRF: разрешён только прямой HTTPS `/migration.php`, редиректы не выполняются, DNS проверяется заново перед каждым запросом, приватные/loopback/link-local/CGNAT/reserved адреса запрещены, а соединение закрепляется за уже проверенным IP. Это предотвращает использование поля migration URL для обращения к localhost, metadata endpoints и внутренней сети нового сервера.

Начиная с 3.5.5 файловые списки миграции читаются потоково по byte-offset и staging индексируется один раз, поэтому большие проекты больше не требуют повторно загружать полный manifest в память и заново обходить всё временное дерево на каждом шаге. После копирования Upgrade Manager строго сверяет SHA-256/размер/права каждого файла, цели symlink и отсутствие лишних старых файлов. Замена домена/пути в БД работает и в таблицах без PRIMARY KEY, а PHP serialized-массивы и обычные объекты переписываются без загрузки пользовательских классов; небезопасные opaque `C:` payload со старым адресом останавливают миграцию и инициируют rollback вместо тихого пропуска.

Начиная с 3.5.6 незавершённая миграция рассчитана на аварийное завершение PHP/HTTP между checkpoint: незакоммиченные хвосты загрузок и manifest автоматически отбрасываются, ZIP восстанавливается до подтверждённого числа записей, а `rewrite_config`, SQL-import, DB-replace и rollback SQL защищены durable crash-intent. Подтверждённый критический блок принимается без повторного выполнения. Если состояние блока доказать нельзя, частично переписанный staging распаковывается заново либо целевая БД очищается и импортируется из исходного дампа перед повторной заменой домена/пути. Поэтому переносы, где новый домен содержит старый (например `example.com` → `newexample.com`), также остаются безопасными. Незавершённые migration job версии 3.5.5 автоматически получают новые byte-checkpoint; legacy-задачи, уже находившиеся в `db_import`, `db_replace` или `rollback_db_restore`, один раз консервативно пересобирают соответствующее состояние, поскольку 3.5.5 ещё не записывал durable intent последнего блока.

Начиная с 3.5.7 готовая migration-ссылка не хранится в browser storage и не возвращается в обычном polling ответа job. После reload, закрытия вкладки или повторного входа Dashboard восстанавливает только факт доступности ссылки из несекретных job-метаданных; сам URL с token расшифровывается из server-side secret sidecar только отдельным авторизованным POST-запросом с CSRF при нажатии «Копировать ссылку». Удаление export-job одновременно отзывает share, а после успешного импорта исходная задача помечается как использованная и ссылка автоматически отзывается.

## Тема интерфейса 3.2.6

Переключатель темы вынесен из раздела **«Настройки»** в левое вертикальное меню, сразу после пункта **«Формат патча»**. Само оформление левого меню не меняется.

Тумблер работает без кнопки «Сохранить»: левое положение — **«Тема: День»**, правое — **«Тема: Ночь»**. При клике тема правой рабочей зоны меняется мгновенно и сразу сохраняется в `settings.json`. При ошибке сохранения интерфейс возвращает прежнюю тему.

Ночная тема по-прежнему меняет только правую рабочую зону: фон, карточки, таблицы, формы, уведомления и модальные окна длительных процессов. Страница входа и Recovery не переключаются.

## Рекомендуемая установка — одним файлом

1. Загрузите `upgrade-installer.php` в корень сайта.
2. Откройте `https://ваш-домен/upgrade-installer.php`.
3. Установщик покажет найденную CMS и доступные возможности.
4. Задайте идентификатор проекта, email администратора и пароль (не менее 8 символов).
5. Установщик создаст `/upgrade/`, уникальные `site_id` и HMAC, затем предложит открыть Upgrade Manager.
6. Никакой отдельный ключ сохранять не нужно: аварийный вход выполняется одноразовой ссылкой на email администратора через центральный сервер Upgrade Manager.
7. После успешной установки удалите `upgrade-installer.php`, если сервер не смог удалить его автоматически.

`config.local.php` не входит в дистрибутив и создаётся только на конкретном сервере. Открытый пароль в нём не хранится — используется bcrypt-хэш. OAuth/runtime-секреты каждой установки остаются отдельными.

## Центральный сервер обновлений Upgrade Manager

### Сброс пароля клиентского Upgrade Manager из главной админки — 3.5.8

На основном сайте с включённым центральным репозиторием в разделе **«Безопасность»** доступна карточка **«Сбросить пароль на клиентском сайте»**. Укажите домен клиента, например `client.example.com`. Центральный сервер проверит публичный `/upgrade/remote-admin.php`, определит `site_id` и отправит одноразовую RSA-подписанную команду.

Временный пароль генерируется только на главном сайте и показывается один раз. На клиент передаётся не пароль, а его bcrypt-хэш. После сброса все прежние cookie-сессии клиента становятся недействительными, lockout очищается, а первый вход по временному паролю принудительно открывает раздел **«Безопасность»** — остальные действия заблокированы до установки постоянного пароля.

Приватный RSA-ключ удалённого управления хранится только в защищённом storage центрального Upgrade Manager и не входит ни в FTP ZIP, ни в сетевой релиз. Клиент закрепляет только публичный ключ, полученный из своего настроенного update-feed и дополнительно проверенный HMAC-ключом репозитория. Команда действует не более трёх минут и содержит одноразовый nonce.

Удалённый сброс пароля из центральной панели работает на клиенте **3.5.8 или новее**.

С 3.6.4 в той же карточке («Доступ к клиентскому сайте») можно выбрать режим **«Установить email и пароль»**: главный сайт задаёт клиенту постоянные логин (email) и пароль, смена при входе не требуется. Передаётся только bcrypt-хэш в одноразовой RSA-подписанной команде. Требуется клиент 3.6.4+. Начиная с 3.6.0 обычный аварийный Recovery выполняется отдельно: пользователь вводит email администратора на `/upgrade/recovery.php`, а одноразовую ссылку отправляет центральный сервер Upgrade Manager.

Начиная с 3.3.8 центральный экземпляр Upgrade Manager сам публикует каждую успешно установленную новую версию для остальных проектов — отдельной ручной публикации нет.

На основном сайте откройте `/upgrade/` → внизу бокового меню нажмите **«Обновление самого Upgrade Manager»** и включите **«Этот сайт — центральный репозиторий»**. Upgrade Manager создаст случайный ключ репозитория и покажет HTTPS update-feed. Затем:

1. устанавливайте на центральный сайт проверенный `upgrade-manager-*-ftp.zip`; версия и описание берутся из его `release.json`;
2. после успешной установки центральный Upgrade Manager автоматически собирает подписанный сетевой релиз;
3. если центральный сайт обновлялся аварийно по FTP, первая загрузка панели или первый запрос клиента к update-feed автоматически обнаружит новую установленную версию и опубликует её;
4. на подключённых сайтах откройте «Обновление самого Upgrade Manager» и нажмите «Проверить обновления»;
5. если версия новее, появится кнопка «Обновить».

На клиентском сайте в разделе «Обновление самого Upgrade Manager» → «Источник обновлений Upgrade Manager» один раз указываются feed URL и ключ центрального сайта. Эти данные хранятся локально и не входят в системный релиз.

Системный релиз **никогда не включает** `config.local.php`, `update-source.local.php`, `.data*` и внутреннее storage. Перед обновлением клиент сохраняет заменяемые файлы в локальный rollback-каталог. При любой ошибке после начала записи старые файлы восстанавливаются автоматически.

Для обновления самого Upgrade Manager `ZipArchive` не требуется: используется собственный bundle `ume-self-update-bundle/1.0` с Base64 payload и SHA-256 каждого файла. Feed подписывается HMAC-SHA256 и доступен только по ключу репозитория. Соединение с центральным сервером разрешается только по HTTPS.

### Ручное самообновление тем же FTP ZIP


### Безопасный экспорт исходников и приватный бэкап Upgrade Manager

На центральном репозитории появилась основная кнопка «Скачать исходный код без секретов»: ZIP содержит только файлы системного релиза, сверенные с `BUILD_SHA256SUMS.txt`, без `config.local.php`, OAuth-токенов и runtime. Этот архив можно передавать разработчику и использовать как исходный код для следующего релиза. При несовпадении контрольных сумм экспорт останавливается.

Приватный полный бэкап для аварийного восстановления по-прежнему доступен отдельно, но его создание требует явного подтверждения владельца; хранить его нужно как пароль, не отправлять в чаты.

На центральном репозитории в разделе «Обновление самого Upgrade Manager» доступна кнопка «Сделать полный бэкап самого себя». После явного подтверждения она формирует ZIP с каталогом `upgrade/` и всеми его файлами, включая `config.local.php` и локальные служебные данные, если они физически расположены внутри `/upgrade/`. База данных сайта не читается и не выгружается. Если storage Upgrade Manager расположен внутри `/upgrade/`, из архива исключаются каталоги `backups/`, `public-backups/` и `rollbacks/`, чтобы в self-backup не попадали резервные копии и rollback-пакеты основного сайта. Функция доступна только центральному репозиторию.

Начиная с 3.3.6 drag & drop самообновления доступен **только на основном сайте, включённом как центральный репозиторий**. Центральный экземпляр принимает тот же полный архив `upgrade-manager-*-ftp.zip`, который используется для аварийной установки по FTP. ZIP должен содержать единственный системный каталог `upgrade/`. После загрузки Upgrade Manager проверяет `release.json`, обязательные файлы и `BUILD_SHA256SUMS.txt`, затем показывает найденную версию и отдельную кнопку установки.

На клиентских сайтах ручная ZIP-зона не показывается, а API загрузки/применения FTP ZIP отклоняет запрос даже при прямом вызове. Клиенты могут обновляться только с настроенного центрального update-feed; на самом центральном сайте сетевое обновление из внешнего feed отключено. После успешного обновления основного сайта Upgrade Manager автоматически собирает подписанный сетевой релиз из уже установленного `/upgrade/` и сразу делает его доступным остальным установкам. Отдельной кнопки публикации больше нет. Если публикация временно завершилась ошибкой, она повторяется автоматически при следующем открытии панели/проверке статуса центрального репозитория.

Во время ручной установки `config.local.php`, `.data/`, локальные OAuth/MCP-токены, настройки и `update-source.local.php` не заменяются. Перед первым изменением создаётся rollback текущих управляемых файлов. При ошибке записи или итоговой SHA-256 проверки предыдущая версия восстанавливается автоматически. Неизвестные пользовательские файлы в `/upgrade/` не удаляются. Для ручного ZIP-самообновления требуется `ZipArchive`, поскольку входной формат — обычный ZIP.

### Сетевой установщик для нового сайта

На центральном сайте: «Обновление самого Upgrade Manager» → кнопка **«Скачать инсталлятор»** (есть только на центральном репозитории). Скачивается файл `upgrade.php`. Это небольшой PHP-файл без полного Upgrade Manager. Положите его в корень нового сайта и откройте в браузере. Он:

- по обычному открытию только показывает страницу с кнопкой «Установить» (боты и превью ссылок ничего не устанавливают);
- после нажатия подключается к центральному update-feed по HTTPS, проверяет HMAC feed, SHA-256 пакета и каждого файла, версию и обязательные файлы;
- атомарно устанавливает `/upgrade/`, сохраняет адрес и ключ репозитория для будущих обновлений;
- при любой ошибке удаляет свои временные файлы — сайт остаётся без изменений;
- удаляет себя и переводит на `/upgrade/setup.php`, выдав этому браузеру одноразовый допуск к настройке на 30 минут.

Завершите настройку (email и пароль) сразу в том же браузере. Если допуск истёк или установка выполнялась вручную по FTP, `setup.php` попросит ключ установки из файла `upgrade/setup-key.local.php` — откройте его через FTP или файловый менеджер хостинга. Посторонний посетитель стать администратором не может.

Таким образом, полный код Upgrade Manager хранится и развивается на одном основном сайте, а на новые сайты переносится только маленький сетевой установщик.

## Автоопределение CMS

Встроенный detector распознаёт:

- WordPress;
- 1С-Битрикс;
- Webasyst + Shop-Script `8.0+`;
- OpenCart;
- Joomla;
- Drupal;
- Magento 2;
- PrestaShop;
- MODX Revolution;
- неизвестный PHP-сайт как `generic`.

Для каждой CMS задаются собственные защищённые конфиги, каталоги медиа/кэша и правила резервирования. Например, `wp-config.php`, `bitrix/.settings.php` или каталог `wa-config` нельзя прочитать через MCP и нельзя изменить патчем. Для Webasyst кодовые backup исключают `wa-data`, `wa-cache` и `wa-log`, а `clear_cache` очищает `wa-cache`.

Если CMS не распознана, Upgrade Manager работает как `generic`-сайт и дополнительно запускает безопасный статический detector MySQL/MariaDB. Он не исполняет PHP-код проекта: ищет типовые `.env`, `config.php`, `config.local.php`, `database.php`, `db.php`, `settings.php` и конфиги в `assets/core`, `app`, `config`, `includes`, `inc`, `core`, затем разбирает `DB_HOST/DB_NAME/DB_USER/DB_PASS`, типовые массивы, wrapper-вызовы вида `*DefineConfig(..., *ConfigEnv(...))`, а также простые literal-подключения через `new PDO("mysql:...")` и `new mysqli(...)`. Если четыре обязательных параметра найдены и доступен `mysqli`, SQL backup/migrations включаются и для обычного PHP-сайта.

## База данных

В 3.0 SQL backup/migrations выполняются через `mysqli` и рассчитаны на MySQL/MariaDB.

- WordPress, OpenCart, Joomla/MySQL, Bitrix/MySQL, Magento 2, PrestaShop, MODX и Webasyst + Shop-Script `8.0+` могут получить полный режим, если параметры БД имеют поддерживаемый вид и доступен `mysqli`. Webasyst читает подключение из `wa-config/db.php`.
- Bitrix/PostgreSQL, Joomla/PostgreSQL и другие движки определяются как неподдерживаемые для SQL в этой версии и работают в файловом режиме.
- Drupal распознаётся как CMS, но его DB-конфигурация намеренно не исполняется универсальным установщиком; до отдельного Drupal DB-adapter используется файловый режим.
- Для `generic` PHP-сайтов 3.2.4 добавляет статическое автоопределение MySQL/MariaDB из распространённых конфигов. PHP-файлы сайта при обнаружении подключения не исполняются.

Если БД недоступна, файловый backup продолжает создаваться без `database.sql`, а причина фиксируется в `manifest.json`/`metadata.json`. Если выбран режим **«Без файлов»** и БД недоступна, создание останавливается с ошибкой, чтобы не получить пустой архив.


## Публичный URL резервной копии 3.2.4

В таблице резервных копий справа от кнопки **«Скачать»** остаётся одна кнопка **«URL»**. Она копирует абсолютный адрес вида `https://example.com/upgrade/public-backup.php?id=backup-....zip`. Вход, cookies, OAuth, HMAC-token и другие параметры доступа не используются.

С 3.2.4 приватный recovery-backup и публичная копия физически разделены. Обычная кнопка **«Скачать»** в авторизованной панели отдаёт исходный recovery ZIP, который используется для отката. Публичный endpoint читает отдельный ZIP из закрытого каталога `public-backups` и никогда не отдаёт приватный recovery-файл.

Публичная копия строится одновременно с backup и автоматически очищается:

- файлы с явными секретами (`.env*`, `config.local.php`, auth/credentials/tokens JSON, private key и высокодостоверные password/secret/token/API-key assignments) не публикуются;
- runtime-данные (`cache`, `tmp`, `logs`, sessions, `admin/system/export`, runtime jobs, OAuth JSON, `history.json`, `applied.json`, `rollback-index.json` и аналогичные служебные файлы) не публикуются;
- SQL-файлы проекта с `INSERT/REPLACE/LOCK TABLES` не публикуются; чистые DDL migrations без строк данных сохраняются;
- даже если приватный backup выбран как «Полный дамп» или «Минимум данных», публичный `database.sql` содержит **только структуру таблиц без INSERT/REPLACE**;
- `manifest.json` публичной копии имеет формат `external-code-backup-share/1.0` и явно сообщает, что копия санитизирована.

HTML-индекс и `format=json` по-прежнему предназначены для ChatGPT: доступны список файлов, preview/raw URL и скачивание **публичного очищенного ZIP** через `download=1`.

Бэкапы, созданные до 3.2.4, не получают публичный URL автоматически: в панели кнопка URL для них отключена. Нужно создать новую резервную копию, чтобы не публиковать старый архив, где могли сохраниться секреты.

**Важно:** URL остаётся полностью публичным. Любой, кто знает адрес, может читать и скачать именно очищенную публичную копию.

## Принудительное продолжение ручного патча 3.1.10

Если ручной ZIP-патч успешно прошёл проверку целостности, SHA-256, подписи, путей и допустимых действий, но не совпал по контексту установки (проект, site_id, домен, минимальная версия PHP или поддерживаемость CMS), в интерфейсе появляется кнопка **«Продолжить всё равно»**. Нажатие разрешает установку только для конкретного загруженного вручную пакета и записывается в журнал как принудительное продолжение.

Повреждённый ZIP, неверная подпись, несовпавшие хэши, защищённые/опасные пути, неподдерживаемые действия и повторно установленный patch_id по-прежнему нельзя обойти этой кнопкой.

## Режимы резервного копирования 3.1.9

Начиная с 3.1.9 файловая часть и база данных выбираются **независимо**. Это даёт 4 × 4 комбинации.

**Настройки файлов:**

1. **Все файлы** — все обычные файлы сайта, включая медиа и документы. Кэш, служебные backup-каталоги, сам Upgrade Manager, защищённые конфиги и пользовательские исключения не архивируются.
2. **Только код + Ядро CMS** — кодовые файлы сайта вместе с распознанным ядром CMS, без медиа и тяжёлых пользовательских файлов.
3. **Только нужные без CMS** — проектный/пользовательский код без известных файлов ядра CMS. Для неизвестной CMS режим работает консервативно: ядро не угадывается и файловая область совпадает с кодовым профилем.
4. **Без файлов** — файловый снимок пустой; при восстановлении файлы сайта не изменяются.

**Настройки БД:**

1. **Полный дамп** — структура и все строки всех таблиц.
2. **Минимум данных** — структура всех таблиц и системные данные; чувствительные категории (заказы, клиенты, пользователи, сессии и т. п.) сохраняются без строк. При восстановлении таблицы, данные которых намеренно не выгружались, не очищаются.
3. **Только структура без данных** — все таблицы через `CREATE TABLE`, без строк. При восстановлении эти таблицы становятся пустыми.
4. **Без БД** — `database.sql` не создаётся, база при восстановлении не изменяется.

Комбинация **«Без файлов» + «Без БД»** запрещена как пустая резервная копия. Правила из блока **«Исключения»** применяются ко всем файловым режимам, кроме «Без файлов».

Новый manifest `external-code-backup/1.4` подписывает SHA-256 архивов, `file_mode`, `database_mode` и список исключений. Восстановление старых копий форматов 1.1–1.3 сохранено с их исходной областью файлов, чтобы обновление менеджера не расширяло удаление при откате старого бэкапа.

## Хранилище

Установщик сначала пытается создать приватное хранилище уровнем выше web-root. Если хостинг не разрешает запись туда, используется случайно именованный каталог внутри `/upgrade/` с `.htaccess`, `web.config`, `index.php` и ограниченными правами. Для Nginx при таком fallback рекомендуется отдельный server-level deny на скрытые каталоги.

## Патчи и rollback

Основной формат — `external-upgrade-patch/1.3` (SQL-миграции требуют 1.3).

- перед изменениями создаётся rollback-пакет;
- защищённые цели берутся из CMS-профиля;
- ручной неподписанный patch 1.1 может быть проверен и локально подписан самим Upgrade Manager;
- `payload_hash` и HMAC проверяются перед применением;
- универсальный post-action — `clear_cache`, который очищает только разрешённые каталоги кэша найденной CMS;
- при ошибке после начала изменений запускается автоматический rollback.

Подробный контракт: `PATCH_FORMAT_RU.md`.

## Подключение ChatGPT и прямой deployment 3.3.4

1. Откройте `/upgrade/` → «API-подключение».
2. Скопируйте MCP URL `https://ваш-домен/upgrade/mcp.php` и добавьте его в ChatGPT как пользовательский удалённый MCP-плагин с OAuth.
3. Upgrade Manager публикует OAuth 2.1 Protected Resource Metadata и Authorization Server Metadata, поддерживает PKCE S256, `resource`, RFC 9207 `iss`, CIMD ChatGPT и DCR.
4. В открывшемся окне войдите в Upgrade Manager и подтвердите доступ. HMAC, пароль и Recovery-ссылки в ChatGPT не передаются.
5. После обновления Upgrade Manager, если набор MCP-действий изменился, в настройках плагина ChatGPT выполните **Refresh / Обновить действия** (или пересоздайте персональный плагин, если Refresh недоступен). ChatGPT использует сохранённый снимок `tools/list` и сам не включает новые действия автоматически.
6. Откройте **новый ChatGPT Work-чат**, введите `@` и выберите Upgrade-плагин для сообщения, в котором нужны MCP-действия.
7. Для проверки вызовите `create_backup` естественным запросом «Создай резервную копию этого сайта» или `list_backups` запросом «Покажи последние бэкапы».
8. После подключения ChatGPT может читать разрешённый код и передавать патч прямо в серверный черновик. ZIP на компьютере пользователя не требуется: Upgrade Manager сам собирает `external-upgrade-patch/1.3`, подписывает и проверяет его.
9. В «Правилах API-обновлений» независимо задаются режим передачи (`После подтверждения` / `Автоматически`) и режим применения (`После подтверждения` / `Автоматически после загрузки`).

Для ресурса `/upgrade/mcp.php` 3.3.4 автоматически создаёт стандартные path-aware discovery-файлы `/.well-known/oauth-protected-resource/upgrade/mcp.php` и `/.well-known/oauth-authorization-server/upgrade/oauth.php`. FTP-сборка по-прежнему содержит только каталог `/upgrade/`, поэтому forwarding-файлы создаются при первом запуске. Для полной совместимости корень сайта должен быть доступен PHP на запись. Состояние обоих маршрутов видно в диагностике раздела «API-подключение».

## Требования и деградация возможностей

Минимум для запуска панели:

- PHP 5.6+;
- возможность записать каталог `/upgrade/` и локальную конфигурацию;
- `json` и `session`.

Дополнительные возможности:

- `ZipArchive` — ZIP-патчи и backup-архивы; системное обновление Upgrade Manager 3.1+ от него не зависит;
- `mysqli` — MySQL/MariaDB backup и SQL-миграции;
- `openssl` — дополнительные криптографические возможности;
- HTTPS — рекомендуется и фактически требуется для нормального удалённого OAuth/MCP подключения.

Установщик не должен отказываться от установки только потому, что `mysqli` или CMS-adapter БД недоступен: он показывает ограниченный режим возможностей.

## Безопасность

- `upgrade/config.local.php` никогда не входит в distributive ZIP;
- CMS-конфиги и `.env` исключены из MCP-чтения и файлового backup-контекста;
- защищённые цели нельзя изменить или удалить патчем;
- внутреннее хранилище не доступно через MCP;
- OAuth-токены хранятся в виде SHA-256;
- прямой MCP-поток принимает только файлы серверного черновика; затем Upgrade Manager сам собирает подписанный ZIP и прогоняет штатную проверку + backup + rollback;
- `patch-profile.json` не содержит HMAC-ключа, DB password, OAuth-токенов или данных Recovery-сессии.

## Ручная установка без one-file installer

Можно загрузить каталог `upgrade/` в корень сайта и открыть `/upgrade/setup.php`. С 3.6.6 страница попросит ключ установки из файла `upgrade/setup-key.local.php` (он создаётся при первом открытии; прочитайте его через FTP). Этот setup использует тот же CMS detector и создаёт тот же универсальный профиль, что и `upgrade-installer.php`.

## Recovery

`/upgrade/recovery.php` принимает email администратора. Если он совпадает с привязанным адресом, центральный сервер Upgrade Manager отправляет одноразовую RSA-подписанную ссылку. Ссылка действует 10 минут, используется один раз и открывает Recovery-сессию на 15 минут. В Recovery доступны безопасная отмена активного процесса, rollback и создание временного пароля.

Постоянного Recovery key в новых установках 3.6.0 нет. Старый `recovery_key`, если он остался в `config.local.php` после обновления прежней версии, кодом 3.6.0 не используется.

### Автоматические полные бэкапы (3.3.4+)

В разделе **Настройки → Автоматическое резервное копирование** можно включить расписание. При сохранении Upgrade Manager пытается создать пользовательскую системную задачу `crontab` автоматически. Задача запускает `upgrade/cron.php` через PHP CLI каждые 5 минут, а фактическая частота backup контролируется настройкой Upgrade Manager.

Для работы без ручной настройки сервера нужны три условия: PHP должен разрешать `exec()`, в системе должны быть доступны `crontab` и PHP CLI, а пользователь PHP-FPM/веб-сайта должен иметь право изменять собственный crontab. Если хотя бы одно условие не выполнено, интерфейс покажет точную причину. Upgrade Manager не подменяет настоящий cron запуском «при посещении сайта», потому что такой режим не гарантирует расписание.

В 3.3.4 установка больше не зависит от временного файла внутри `.upgrade-manager-*/temp`: сначала используется стандартный `crontab -` через STDIN, а для несовместимых реализаций — системный временный каталог. Статус считается успешным только после повторной проверки `crontab -l`.

Автоматический backup использует профиль **Все файлы + Полный дамп БД**. Пользовательские исключения файлов продолжают действовать. Если база данных недоступна, автоматический полный backup считается неуспешным.

## Бэкап для GPT и инструкция подписи — 3.7.1

Всякий вновь созданный приватный или очищенный публичный ZIP бэкапа сайта содержит в корне `00_START_HERE_FOR_GPT.md`, `AGENTS.md`, `PATCH_AUTHORING_RU.md`, `PATCH_FORMAT_RU.md`, `PATCH_BUILDER.py`, профиль сайта и тестовый шаблон манифеста. Также в корне ZIP есть каталог `upgrade/` с полным набором **проверенных SHA-256 файлов управляемого кода Upgrade Manager**, без HMAC-ключей, `config.local.php`, OAuth-токенов и runtime. Список хэшей — в `upgrade-source-manifest.json`; восстановление сайта игнорирует эту справочную папку. При повреждённых системных SHA-256 бэкап не публикуется.

`PATCH_BUILDER.py` создаёт ZIP 1.3 для авторизованной **ручной** загрузки. В нём отсутствуют `payload_hash` и `signature` одновременно; Upgrade Manager вычислит и поставит оба поля на сервере по своему ключу. Для полностью подписанного ZIP до загрузки следует использовать защищённые MCP/API-инструменты, а не раскрывать HMAC-ключ. В `00_START_HERE_FOR_GPT.md` подставляются версии и ID конкретного сайта, поэтому GPT больше не должен их угадывать.

На центральном self-backup и очищенном экспорте исходников также находится корневая инструкция `00_START_HERE_FOR_GPT.md`: для обновления самого репозитория используйте **полный FTP ZIP**, не обычный патч сайта. Приватный self-backup по-прежнему содержит секреты и не предназначен для передачи GPT.
