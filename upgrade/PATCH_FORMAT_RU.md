# Формат патча Universal Upgrade Manager 3.7.4

Для новых патчей используется `external-upgrade-patch/1.3`. Форматы 1.0/1.1/1.2 поддерживаются для файловых обновлений без SQL-миграций. Старые форматы не защищали `migrations.tables`: патчи с SQL-миграциями в форматах до 1.3 отклоняются. У каждого патча `version` обязана точно совпадать со следующей версией сайта.

## ZIP

```text
patch.zip
├── manifest.json
├── payload/
│   └── ...
└── migrations/
    └── 001-change.sql
```

Минимальный манифест 1.3 до подписи:

```json
{
  "format": "external-upgrade-patch/1.3",
  "patch_id": "unique-id",
  "name": "Название",
  "base_site_version": "1.6.4",
  "version": "1.6.5",
  "project": "идентификатор проекта",
  "domain": "example.ru",
  "site_id": "идентификатор сайта",
  "php_min": "5.6.0",
  "files": [],
  "delete": [],
  "migrations": [],
  "actions": {"clear_cache": true}
}
```

Подписанный манифест дополнительно обязан содержать `payload_hash` и `signature`. В 1.3 `base_site_version` берётся из backup, а `version` обязана быть равна `next_patch_version` из того же backup.

## Ручная загрузка в Upgrade Manager 3.0+

Рекомендуемый режим: загрузить корректный ZIP 1.3 **без** `payload_hash` и `signature`. Неподписанные файловые патчи 1.2 также автоматически подписываются; если в неподписанном 1.2 есть SQL-миграции, менеджер переводит его в безопасный формат 1.3 перед подписью. Уже подписанные SQL-патчи 1.2 требуют пересборки. После авторизованной загрузки Upgrade Manager сам:

1. проверяет проект, `site_id`, домен, пути и SHA-256;
2. пересчитывает `payload_hash` по фактическому ZIP;
3. подписывает HMAC локальным ключом из `upgrade/config.local.php`;
4. заменяет `manifest.json` внутри защищённой копии ZIP;
5. повторно запускает обычный валидатор подписи.

Если `payload_hash` и `signature` уже присутствуют, пакет не переподписывается и проверяется как раньше. Нельзя передавать только одно из этих двух полей.

## API/MCP 3.3.4

Основной MCP-поток больше не требует локальной сборки ZIP. Агент создаёт серверный черновик через `begin_patch_draft`, передаёт файлы/миграции и вызывает `finalize_patch_draft`. Upgrade Manager формирует `manifest.json`, сам назначает `version = next_patch_version`, вычисляет SHA-256, `payload_hash` и HMAC-подпись локально, собирает ZIP 1.3 и прогоняет обычный валидатор.

Поток `authorize_patch` → `begin_patch_upload` → чанки → `finish_patch_upload` сохранён для обратной совместимости с внешними ZIP-пакетами. Полученный от `authorize_patch` манифест менять нельзя.

## Расчёт payload_hash

Для 1.3 сначала фиксируется контекст версии, затем строки добавляются строго в порядке массивов манифеста:

```text
BASE_SITE_VERSION:<base_site_version>\n
TARGET_SITE_VERSION:<version>\n
<target>:<sha256>\n
DELETE:<path>\n
SQL:<migration_id>:<sha256>\n
TABLES:<migration_id>:<sha256(canonical-json(tables))>\n
ACTIONS:<sha256(canonical-json(actions))>\n
```

Для 1.1/1.2/1.3 строка `ACTIONS` присутствует всегда, даже если `actions` пустой объект. Строки `BASE_SITE_VERSION` и `TARGET_SITE_VERSION` присутствуют в 1.2/1.3. Строка `TABLES` включается после соответствующей строки `SQL` только в 1.3 и подписывает точный массив таблиц для rollback. Форматы до 1.3 с SQL-миграциями не принимаются.

```text
payload_hash = SHA256(payload_string)
```

Канонический JSON: ключи объектов сортируются рекурсивно по строке, порядок массивов сохраняется, Unicode и `/` не экранируются.

## Подпись

```text
message = patch_id|site_id|domain|payload_hash
signature = HMAC-SHA256(message, hmac_key)
```

`hmac_key` хранится только в `upgrade/config.local.php`. Он **не входит в бэкап, профиль сайта, документацию или MCP**. Для ручной загрузки 3.0+ передавать этот ключ разработчику не требуется: сервер подпишет неподписанный ZIP сам.

Проверяемый тестовый пример с фиктивным ключом находится в `PATCH_SIGNATURE_EXAMPLE.json`. Это только пример алгоритма и он не подходит для реального сайта.

## files

```json
{
  "source": "payload/catalog/controller/example.php",
  "target": "catalog/controller/example.php",
  "sha256": "64 hex symbols"
}
```

SHA-256 считается от точных байтов файла внутри ZIP. После расчёта хэша файл менять нельзя.

## migrations

```json
{
  "id": "001-example",
  "source": "migrations/001-example.sql",
  "sha256": "64 hex symbols",
  "tables": ["{{DB_PREFIX}}example"]
}
```

`tables` обязан перечислять все таблицы, которые может изменить SQL: по этому списку создаётся rollback-снимок. В SQL разрешён `{{DB_PREFIX}}`. В формате 1.3 список таблиц криптографически привязан к подписи; изменение порядка, удаление или замена таблицы делает подпись недействительной.

## delete и безопасность rollback

Удалять существующий каталог целиком запрещено. Для корректного rollback перечисляйте удаляемые файлы по одному.

Защищённые цели формируются автоматически из CMS-профиля. Например, WordPress защищает `wp-config.php`, 1С-Битрикс — `bitrix/.settings.php` и `bitrix/php_interface/dbconn.php`, OpenCart — корневой и admin `config.php`; всегда защищены `.env`, `.git`, весь каталог `/upgrade/` (сам Upgrade Manager, включая `config.local.php`) и внутреннее хранилище Upgrade Manager — с 3.6.3 это проверяется независимо от `protected_targets` установки. Абсолютные пути, `..`, Windows drive paths и симлинки не допускаются.

## actions

В 1.2 основной универсальный action:

```json
{"clear_cache": true}
```

Он очищает только каталоги кэша, разрешённые адаптером обнаруженной CMS. Для обратной совместимости с патчами OpenCart 2.x также принимается `clear_opencart_cache`, но новые патчи должны использовать `clear_cache`. Другие действия отклоняются.

## Версия сайта (3.7.0)

Версия сайта и `manifest.version` теперь едины. Backup фиксирует `site_version` и `next_patch_version`. Новый патч обязан иметь `base_site_version = site_version` и `version = next_patch_version`; произвольные номера вроде `1.8.0` для сайта `1.6.4` отклоняются. Шаг равен 0.0.1, при этом последняя цифра работает как десятичный счётчик: `1.0.8 → 1.0.9 → 1.1.0 → … → 1.9.9 → 2.0.0`. При rollback возвращается точная `site_version_before`, сохранённая при установке.

## Что находится в каждом новом бэкапе (3.7.1+)

И в приватном, и в очищенном публичном backup ZIP в КОРНЕ лежат (если БД недоступна, `database.sql` может отсутствовать):

- `00_START_HERE_FOR_GPT.md` — **первый файл для GPT**, пошаговый порядок, реальные site_id/project/domain/site_version/next_patch_version, точное объяснение подписей;
- `AGENTS.md` — обязательное краткое правило для кодовых агентов;
- `PATCH_AUTHORING_RU.md` — инструкция по сборке;
- `PATCH_FORMAT_RU.md` — данный алгоритм `payload_hash` и HMAC;
- `patch-profile.json` — безопасный машинный профиль этого сайта;
- `PATCH_UNSIGNED_MANIFEST_TEMPLATE.json` — актуальный шаблон 1.3;
- `PATCH_SIGNATURE_EXAMPLE.json` — HMAC-пример с **фиктивным** ключом;
- `AGENT_WORKFLOW_RU.md` — серверный MCP-процесс;
- `PATCH_BUILDER.py` — локальная безопасная сборка ZIP-патча для ручной загрузки, без внешних Python-зависимостей;
- `upgrade-source-manifest.json` — SHA-256 проверенных исходников системы;
- `upgrade/` — **весь управляемый код самой установленной версии Upgrade Manager**, включая PHP, JS, CSS, инструкции, release.json и BUILD_SHA256SUMS.txt.

Исходники `upgrade/` берутся строго из SHA-256 проверенного списка системных файлов. Закрытые конфиги (`upgrade/config.local.php`), ключи, OAuth/runtime и неучтённые файлы **никогда** не экспортируются в эти справочные исходники. `upgrade/` не входит в `site-files.zip` и не восстанавливается при восстановлении сайта. Его нельзя изменять обычным патчем сайта.

Папка `upgrade/` передаётся GPT, чтобы он проверял актуальный код валидатора, а не придумывал формат подписи по памяти. **Невозможно создать заранее подписанный офлайн-патч без закрытого HMAC-ключа**. Для РУЧНОЙ загрузки создавайте полноценный ZIP 1.3, у которого одновременно отсутствуют `payload_hash` и `signature`: сервер добавляет оба после авторизованной загрузки. Для MCP используйте серверные draft-tools.


## Ручное продолжение при несовпадении контекста (3.1.10)

Для ручной загрузки из авторизованного интерфейса менеджер отделяет проверки целостности/безопасности от проверок совместимости. После успешной проверки ZIP, путей, SHA-256, payload_hash, HMAC-подписи и допустимых действий владелец может явно продолжить установку при несовпадении project, site_id, domain, php_min или статуса поддержки CMS. API-загрузка такого обхода не получает.
