# С чего начать, если вам дали backup Upgrade Manager

Эта инструкция предназначена разработчику или AI-агенту, который получил ZIP-бэкап сайта и должен подготовить патч. **Сначала прочитайте `00_START_HERE_FOR_GPT.md` из корня бэкапа.**

1. Откройте `patch-profile.json` в корне backup ZIP. Используйте из него `site_id`, `project`, разрешённые домены, текущую версию Upgrade Manager и возможности ручной загрузки.
2. Сначала прочитайте `manifest.json` backup: `site_version` — версия снимка, `next_patch_version` — единственная допустимая версия следующего патча. Используйте `external-upgrade-patch/1.3`, укажите `base_site_version = site_version`, а `version = next_patch_version`. Никогда не придумывайте номер патча самостоятельно.
3. Соберите `manifest.json`, `payload/` и при необходимости `migrations/`. SHA-256 в `files` и `migrations` должны совпадать с точными байтами внутри ZIP.
4. Для ручной drop-zone Upgrade Manager 3.0+ **не нужно получать HMAC-ключ**: оставьте одновременно отсутствующими `payload_hash` и `signature`. Авторизованный Upgrade Manager проверит ZIP, локально рассчитает оба поля и повторно валидирует пакет.
5. Если вы уже получили полностью подписанный манифест, оставьте `payload_hash` и `signature` как есть — менеджер проверит их и не станет переподписывать.
6. Для MCP/API 3.3.4 основной путь — `begin_patch_draft` → `put_patch_file` / `put_patch_migration` → `finalize_patch_draft`. ZIP, SHA-256 и подпись собирает сам Upgrade Manager на сервере. Старый `authorize_patch` остаётся только для совместимости с уже собранным внешним ZIP.
7. Никогда не пытайтесь восстановить HMAC из подписи бэкапа. Реальный `hmac_key` намеренно отсутствует в backup и профиле.
8. Перед релизом проверьте: уникальный `patch_id`, отсутствие запрещённых путей, SHA-256 каждого файла, полный `tables` у каждой SQL-миграции, отсутствие удаления каталога целиком и PHP-совместимость сайта.

Полный алгоритм: `PATCH_FORMAT_RU.md`.
Шаблон: `PATCH_UNSIGNED_MANIFEST_TEMPLATE.json`.
Проверяемый пример подписи: `PATCH_SIGNATURE_EXAMPLE.json`.

Примечание о бэкапе 3.0+: `database.sql` формируется с реальными переводами строк после `VALUES`; строка `VALUES\\n(` не должна встречаться как буквальные символы.

## С 3.7.1 — обязательная инструкция и код самого менеджера в каждом backup

В корне КАЖДОГО вновь созданного backup ZIP (как приватного, так и очищенного для GPT) находятся `00_START_HERE_FOR_GPT.md` и `AGENTS.md`. **Начинайте с них**: инструкции автоматически заполняются реальными `site_id`, `project`, `base_site_version`, `next_patch_version` из этого бэкапа.

В корне дополнительно лежат `PATCH_BUILDER.py` (автоматическая сборка корректного ZIP для ручной загрузки), `upgrade-source-manifest.json` (SHA-256 исходников) и `AGENT_WORKFLOW_RU.md`. В отдельном каталоге `upgrade/` находится полный проверенный код самой установленной версии Upgrade Manager из списка `BUILD_SHA256SUMS.txt`. Секретные и runtime-файлы в нём исключены. Эта папка включена только для чтения: **НЕ ДОБАВЛЯЙТЕ `upgrade/` в payload патча сайта**.

Быстрая сборка на Python 3:

```bash
python PATCH_BUILDER.py --backup backup.zip --changes changes --name "Исправление сайта" --out patch.zip
```

Этот `patch.zip` содержит `manifest.json` формата 1.3 и правильные SHA-256, но **не содержит HMAC-подписи до авторизованной ручной загрузки**. Менеджер 3.7.0+ безопасно добавляет `payload_hash` и `signature` на своём сервере. Для полностью подписанного ZIP вне админки требуется серверная авторизация через MCP/API; в бэкапе секретного HMAC-ключа нет.
