# Обязательный регламент агента Upgrade Manager 3.7.4

1. Если дан backup ZIP без прямого MCP-доступа: **первым открыть `00_START_HERE_FOR_GPT.md` и `AGENTS.md` в корне**, затем `PATCH_FORMAT_RU.md` и код `upgrade/lib/Manager.php`. Подготовить ручной ZIP 1.3 через `PATCH_BUILDER.py` с серверной автоподписью; не подделывать `payload_hash` и HMAC. Если доступен MCP, сначала вызвать `get_site_status` и проверить домен/проект/`site_version`/`next_patch_version`, а также `deployment_policy`. Версию патча не придумывать: она обязана быть ровно `next_patch_version`; серверный `begin_patch_draft` назначает её автоматически.
2. До изменения кода создать `create_task` с полным ТЗ и критериями приёмки.
3. Читать только релевантные файлы через `list_files`, `read_files`, `search_code`. Не пытаться читать конфиги, токены, HMAC, Recovery-ссылки/сессии и другие закрытые пути.
4. Значимые решения и проверки фиксировать через `append_task_log`.
5. Основной путь передачи изменений: `begin_patch_draft` → один или несколько `put_patch_file` / `put_patch_migration` → `finalize_patch_draft`.
6. Не просить пользователя скачивать ZIP на компьютер, если прямой MCP-поток доступен. ZIP собирает, подписывает и проверяет сам Upgrade Manager.
7. Соблюдать `patch_upload_mode`: при `confirm` до `begin_patch_draft` получить явное согласие пользователя; при `auto` передавать подготовленные изменения сразу.
8. После `finalize_patch_draft` соблюдать `patch_apply_mode`: при `confirm` попросить владельца нажать «Разрешить установку» в Upgrade Manager → «API-задачи» и только затем вызвать `start_deployment` (без этого сервер вернёт `awaiting_owner_approval`); при `auto` deployment уже запускается сервером.
8a. Файлы каталога `/upgrade/` и storage Upgrade Manager не являются допустимыми целями патча — сервер отклонит такой черновик.
9. После старта повторять `advance_deployment` до `completed`, `failed` или `cancelled`. Не объявлять успех, пока статус не терминальный.
10. Если требуется бэкап, `start_deployment`/`advance_deployment` сами сначала создают его. Не обходить эту защиту.
11. При ошибке дождаться завершения штатного rollback. Зафиксировать точную ошибку в журнале и не сообщать об успешной установке.
12. После установки выполнить доступные профильные проверки сайта и сохранить только реально выполненные проверки.
13. Вызвать `finish_task`. `completed` допустим только после успешной установки и с непустым списком validation checks.
14. Старые инструменты `authorize_patch`, `begin_patch_upload`, `upload_patch_chunk`, `finish_patch_upload`, `start_patch_install` использовать только для совместимости с уже собранным внешним ZIP.

## Высокоуровневые операции без отдельного ТЗ

- Для прямой просьбы пользователя «создай бэкап» используйте `create_backup`; сервер сам создаст служебную API-задачу. Затем повторяйте `advance_job` до терминального статуса.
- Для просмотра копий используйте `list_backups`; для передачи бэкапа в ChatGPT используйте `get_backup_download_url`, который возвращает только очищенную публичную копию.
- Для изменения кода по ТЗ продолжайте использовать полный поток `create_task` → server-side patch draft → deployment, описанный выше.

## Автоматические backup

Начиная с 3.3.4 Upgrade Manager может сам установить пользовательский system cron для полного backup. При диагностике различайте настоящий установленный crontab и просто включённую настройку: рабочее состояние — `enabled=true`, `system_cron_installed=true`, `active=true`.
В 3.3.4 основной способ записи — STDIN (`crontab -`), fallback — системный temp; поле `cron_install_method` показывает реально использованный способ.

## Подпись SQL и подтверждение отката в 3.7.0

Для SQL-миграций используйте только формат `external-upgrade-patch/1.3`: список `migrations.tables` входит в HMAC-подписываемый payload. При `patch_apply_mode=confirm` вызов MCP `start_patch_rollback` не запускает откат до явного разрешения владельца в разделе «API-задачи»; после разрешения повторите вызов.

## Политика самообновления 3.3.8

Прямая загрузка полного FTP ZIP Upgrade Manager разрешена только установке, где включён режим центрального репозитория. Клиентские установки не принимают произвольный self-update ZIP и обновляются только подписанными релизами центрального update-feed. Центральная установка не применяет remote self-update из внешнего feed: она обновляется вручную полным FTP ZIP, после успешной установки новая версия автоматически публикуется для клиентов. Ручной отдельной операции публикации в 3.3.8 больше нет.

## Состав backup 3.7.1

Обычные и публичные бэкапы содержат в корне `00_START_HERE_FOR_GPT.md`, `AGENTS.md`, `PATCH_BUILDER.py`, `upgrade-source-manifest.json` и полный SHA-256 проверенный код `/upgrade/` (без секретов). Обычный патч сайта не должен изменять `/upgrade/`. Для центрального репозитория обновление самого менеджера выполняется полным FTP ZIP, а не site patch.
