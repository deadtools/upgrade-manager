# Прямое подключение ChatGPT к Upgrade Manager 3.7.4

В `get_site_status` возвращаются `site_version` и `next_patch_version`. Для прямого MCP-патча версия назначается сервером автоматически и всегда равна `next_patch_version`; AI не должен придумывать номер версии.

## MCP URL

Для подключения нужен только адрес из раздела «API-подключение»:

```text
https://ваш-домен/upgrade/mcp.php
```

ChatGPT обнаруживает OAuth 2.1 автоматически через Protected Resource Metadata и Authorization Server Metadata. Upgrade Manager поддерживает PKCE S256, `resource`, RFC 9207 `iss`, CIMD ChatGPT и DCR. Пароль Upgrade Manager, HMAC, Recovery-ссылки и OAuth-токены в чат передавать не нужно.

### После обновления MCP-инструментов

ChatGPT сохраняет снимок обнаруженных действий плагина. После обновления Upgrade Manager, которое меняет `tools/list`, откройте настройки созданного плагина и выполните **Refresh / Обновить действия**. Если такой кнопки нет, удалите и создайте персональный MCP-плагин заново. Затем откройте **новый ChatGPT Work-чат**, введите `@` и выберите ваш Upgrade-плагин для сообщения, которому нужны действия.

В 3.3.4 доступны высокоуровневые инструменты резервных копий:

- `create_backup` — сразу запускает штатный backup с текущими настройками файлов и БД и автоматически создаёт служебную API-задачу;
- `list_backups` — показывает последние резервные копии;
- `get_backup_download_url` — возвращает очищенную публичную ссылку для ChatGPT и прямую ссылку на публичный ZIP.

Для патчей основным остаётся серверный поток `begin_patch_draft` → `put_patch_file` / `put_patch_migration` → `finalize_patch_draft` → `start_deployment` / `advance_deployment`.

## Новый прямой deployment

В 3.3.4 основной сценарий больше не требует скачивать ZIP на компьютер пользователя:

1. ChatGPT вызывает `get_site_status` и создаёт `create_task` с полным ТЗ.
2. Читает только разрешённые исходники сайта.
3. По сохранённой политике либо спрашивает разрешение на передачу патча, либо сразу вызывает `begin_patch_draft`.
4. Передаёт новые/изменённые файлы через `put_patch_file`; SQL-миграции — через `put_patch_migration`.
5. `finalize_patch_draft` заставляет сам Upgrade Manager собрать ZIP `external-upgrade-patch/1.3`, вычислить SHA-256, подписать локальным HMAC и повторно проверить пакет.
6. Если применение требует подтверждения, ChatGPT останавливается на `ready_for_approval`. После согласия пользователя вызывает `start_deployment`.
7. Если включено авто-применение, `finalize_patch_draft` сразу запускает deployment.
8. `advance_deployment` автоматически проводит обязательный бэкап (если включён), затем установку и возвращает состояние до `completed`, `failed` или `cancelled`.
9. При ошибке установки штатный механизм Upgrade Manager выполняет rollback.
10. После проверки результата ChatGPT сохраняет итог через `finish_task`.

Старый поток `authorize_patch` + чанковая загрузка ZIP оставлен для совместимости.

## Политика подтверждений

В «API-подключение → Правила API-обновлений» есть два независимых параметра:

- **Передача патча из ChatGPT**: `После подтверждения` / `Автоматически`.
- **Применение патча**: `После подтверждения` / `Автоматически после загрузки`.

С версии 3.6.3 режим «После подтверждения» для применения обеспечивается сервером: пока владелец не нажмёт «Разрешить установку» в карточке API-задачи, `start_deployment` возвращает `awaiting_owner_approval` и ничего не устанавливает.

Даже в автоматическом режиме интерфейс ChatGPT может дополнительно показать собственное подтверждение write/destructive action в соответствии с разрешениями плагина. Это нормальная дополнительная защита клиента.

## OAuth discovery

Для URL `/upgrade/mcp.php` Upgrade Manager публикует стандартные path-aware metadata:

```text
/.well-known/oauth-protected-resource/upgrade/mcp.php
/.well-known/oauth-authorization-server/upgrade/oauth.php
```

Поскольку FTP-сборка содержит только каталог `/upgrade/`, 3.3.4 автоматически создаёт эти два маленьких forwarding-файла в корневом `/.well-known/` при первом запуске. Корень сайта должен быть доступен PHP на запись. Состояние discovery показывается прямо на странице «API-подключение».

Если корень сайта недоступен на запись, сам MCP endpoint продолжит отдавать `WWW-Authenticate` с прямой ссылкой на metadata, но для максимально совместимого автоматического обнаружения рекомендуется исправить права на `/.well-known/`.

## Безопасность

- access/refresh tokens хранятся только в виде SHA-256;
- токены привязаны к точному MCP `resource`;
- запись разрешена только через штатные инструменты с OAuth scopes;
- защищённые пути (`config.local.php`, `.env` и другие правила установки) через MCP не читаются и не изменяются;
- серверный патч проходит ту же проверку подписей, SHA-256, project/site/domain, безопасных путей и миграций, что и ручной ZIP;
- автоматический rollback для прямой установки отключить нельзя.

## Отключение

В «API-подключение» можно выключить прямой API или нажать «Отключить все подключения». Access/refresh tokens будут отозваны; обычная работа Upgrade Manager останется доступной.

## Системный cron для автоматических backup (3.3.4+)

Планировщик реализован отдельным CLI-entrypoint `cron.php`. Веб-доступ к нему возвращает 404. При включении расписания Upgrade Manager добавляет в пользовательский crontab одну маркированную строку вида `*/5 * * * * php /path/to/upgrade/cron.php --auto-backup ...`. Повторное сохранение не создаёт дубликаты; отключение удаляет свою строку, а если удалить её невозможно, runner всё равно увидит отключённую настройку и ничего не выполнит.

Начиная с 3.3.4 содержимое crontab передаётся в `crontab -` через STDIN. Это устраняет зависимость от видимости приватного runtime-каталога сайта для системного helper-а `crontab`. Если конкретная реализация `crontab` не принимает STDIN, используется проверенный временный файл из `sys_get_temp_dir()`, после чего результат обязательно перечитывается через `crontab -l`.

## Политика самообновления 3.3.8

Прямая загрузка полного FTP ZIP Upgrade Manager разрешена только установке, где включён режим центрального репозитория. Клиентские установки не принимают произвольный self-update ZIP и обновляются только подписанными релизами центрального update-feed. Центральная установка не применяет remote self-update из внешнего feed: она обновляется вручную полным FTP ZIP, после успешной установки новая версия автоматически публикуется для клиентов. Ручной отдельной операции публикации в 3.3.8 больше нет.

## Откат через MCP (3.7.0)

Если `patch_apply_mode=confirm`, первый `start_patch_rollback` возвращает `approval.status=awaiting_owner_approval` и ничего не меняет. Владелец открывает Upgrade Manager → «API-задачи», проверяет `patch_id` и нажимает «Разрешить откат». Разрешение действительно 15 минут для точной пары task_id/patch_id. Повторный `start_patch_rollback` начинает откат и возвращает job; после запуска разрешение повторно не используется. При политике `auto` откат начинается сразу.

## Офлайн-бэкапы для GPT — 3.7.1

Новый ZIP (включая публичную очищенную копию) содержит корневой `00_START_HERE_FOR_GPT.md`, `AGENTS.md`, проверенные исходники `upgrade/`, `PATCH_BUILDER.py` и полный контракт SHA-256/HMAC. Используйте их при отсутствии активного MCP. Вручную загружаемый ZIP может не содержать оба поля `signature` и `payload_hash` — менеджер подписывает его после авторизованной загрузки. MCP/API старого типа такой неподписанный ZIP не принимает: используйте `begin_patch_draft` и `finalize_patch_draft`.
